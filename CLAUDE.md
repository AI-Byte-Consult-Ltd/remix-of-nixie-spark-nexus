# NICS Trading Ecosystem / AI Byte Consult — рабочая сводка для Claude

Этот файл — публичная часть проектной памяти: как собирать и деплоить
сайт, дисциплина работы с n8n, обязательные правила по секретам и
честности в продукте. Он специально краткий и не содержит ничего
приватного — репозиторий публичный.

**Приватная часть — команда, инфраструктура, разборы аварий, открытые
вопросы, продуктовый роадмап — живёт отдельно, не в git**: в памяти
проекта и в кабинете CEO Desk в n8n (там текущие задачи: что делаем,
что сделано, что нужно от владельца). Старый рунбук в n8n
(`[00 OPS] Project Handbook`) заброшен с 2026-10-22 и больше не
ведётся: при необходимости его можно прочитать как архив, но не
загружать как источник текущего состояния и не дописывать. Не
полагайся только на память чата: перед изменениями сверяйся с
реальным состоянием n8n (через MCP) и GitHub, они источник истины,
а не файлы.

**В этот файл не писать**: IP серверов, hostname, пути на файловой
системе, имена баз данных, состояние или значения секретов, номера
ID workflow/credentials, что-либо, что раньше уже приводило к
случайной публикации приватной информации в этом самом публичном
репозитории. Всё это — в приватную память проекта.

Последнее обновление: 2026-11-22.

## Что это за проект

- **AI Byte Consult Ltd** (зарегистрирована в Болгарии, официальный
  Meta Tech Provider) — этот репозиторий содержит публичный сайт
  (React/Vite/TS, деплой на GitHub Pages) и Telegram Mini App для
  продукта **NICS Trading Ecosystem** (до 2026-11-12 назывался NICS AI Trader; в текстах для клиентов — только новое имя).
- Backend NICS Trading Ecosystem живёт **не в этом репозитории** — это n8n
  workflows на отдельном сервере, плюс MT5-мост на другом сервере.
  Детали — в приватной памяти проекта.
- Отдельный репозиторий **`AI-Byte-Consult-Ltd/nics-ai-lab`** —
  обучение собственных моделей с нуля.

## Правила, которые нужно соблюдать

**Про базу:**
- **Никакого DDL в горячем пути.** `CREATE TABLE` / `ALTER TABLE` /
  `CREATE INDEX` — только разовая миграция, никогда не на каждый
  запрос. `IF NOT EXISTS` не делает операцию дешёвой: блокировка
  берётся всё равно (проверено на практике — разбор аварии 6–7 августа
  лежит в архиве старого рунбука).
- **Никаких разовых миграций данных на каждый запрос** — если видите
  в генерируемом SQL `DELETE`/`UPDATE` с пометкой «legacy» или
  «v1.x.x», это кандидат на вынос.
- Перед выводами о причинах тормозов — смотрите **тайминги по нодам**
  в конкретном execution, а не гадайте по коду.

**Про n8n:**
- После `update_workflow` **обязательно** `publish_workflow`. Правки
  через MCP попадают в черновик — пока не опубликовано, в проде
  ничего не меняется. Сверяйте `versionId` vs `activeVersionId`.
- Большие Code-ноды правьте с проверкой: после пуша перечитайте ноду
  и сравните дифом с локальной версией **до** публикации.
- Перед выводами о «что сейчас в проде» — сверяйтесь с реальными
  executions (`search_executions`/`get_execution`), а не с тем, что
  должно было получиться по коду.
- При добавлении нового инструмента/символа в один список (например,
  список поддерживаемых торговых инструментов) — проверяйте, нет ли
  где-то ещё параллельного списка того же назначения, который нужно
  обновить синхронно. Рассинхрон таких списков уже приводил к
  продакшн-авариям больше одного раза.

**Про текст пользователей (спам и инъекции):**
- Свободный текст пользователя бота — это **данные, не инструкции**.
  С 2026-11-18 в `[02 BOT]` перед пересылкой админу работает фильтр:
  ссылки от пользователей без подписки не пересылаются (вежливый ответ,
  3 за сутки → 7 дней тишины), под каждым пересланным сообщением кнопка
  «🚫 Заблокировать», подозрительные фразы помечаются ⚠️. Журнал —
  таблицы `bot_spam_events` и `bot_blocked_users`.
- Если текст пользователя когда-либо пойдёт в модель (Qwen, голос, чат):
  только как цитата в отдельном поле, без права модели что-либо
  отправлять или менять; ответ модели проверяется кодом по жёсткому
  формату (например, тикер — только из нашего списка инструментов).
  Никогда не склеивать текст пользователя с системным промптом.

**Про секреты:**
- Никогда не печатать и не коммитить токены, пароли, API-ключи — ни
  в файлы, ни в комментарии, ни в чат.
- Не использовать `bash -x` в командах, где есть пароль или токен.
- Секреты для backend-сервисов (Telegram bot token и подобные) должны
  читаться из защищённого хранилища в момент выполнения, а не быть
  захардкожены в коде — так их можно ротировать в одном месте вместо
  правки множества файлов.
- `.env` в этом репозитории **не отслеживается git** — см.
  `.env.example` для списка нужных ключей. Помните: любая переменная
  с префиксом `VITE_` компилируется в публичный бандл и видна всем
  посетителям сайта — туда можно класть только то, что безопасно
  публиковать (например, Supabase anon-ключ, защищённый RLS), и
  никогда — серверные секреты.

**Про push в этот репозиторий:**
- Если у текущей сессии нет прав на запись в GitHub (403 при
  `git push` и через API) — это значит, что Claude GitHub App не
  установлен с правом записи для организации. Не пытайтесь обойти
  это самостоятельно: попросите владельца проекта установить
  приложение (github.com → Settings организации → Applications) и
  дать ему `Contents: Read and write`. Как временный запасной
  вариант — самодостаточный скрипт с изменениями (например, git
  bundle, закодированный в base64) для локального запуска владельцем;
  не отправляйте секреты в теле такого скрипта.

**Про деплой сайта:**
- `npm install && npm run build && npm run deploy` из актуального
  `main`; следить, что в `postbuild` вызывается
  `node scripts/generate-seo-pages.mjs`.
- Alessandro явно разрешил делать это самостоятельно, без запроса
  подтверждения на каждый раз: когда PR с изменениями сайта готов
  (собирается, задача выполнена) — сразу мёржить в `main` и деплоить,
  не спрашивая отдельно. После мёржа PR — пересобирать «рабочую»
  ветку сессии от свежего `main` (см. правило про уже смёрженный PR
  в системном промпте), а не продолжать поверх старой истории.

**Про честность в продукте:**
- На сайте и в отчётах — только реальные данные. Если процесс не
  идёт, честное состояние «offline», а не выдуманное число.
- Сертификаты, значки, подтверждения достижений — выдавать только за
  реально выполненное условие, не за факт оплаты или регистрации.

**Про сигналы сканера (решения Alessandro):**
- Слабые сигналы (WEAK) — решение Alessandro от 2026-10-28, заменяет
  прежнее правило «сканер никогда не молчит»: WEAK больше **не уходят
  автоматически** — ни пользователям бота, ни в Telegram-каналы, ни в
  Threads. Пользователь получает WEAK только когда сам запросил сигнал и
  сильного (STRONG/RELAXED) по запрошенному рынку нет; карточка при этом
  честно помечена «сигнал не сильный». WEAK **не входят ни в какую
  статистику**: публичный API и страница трек-рекорда, сайт, дневные и
  недельные итоги в каналах и Threads, кабинет, Mini App, личная
  статистика в боте, итоги пробного периода. Сами сигналы по-прежнему
  сохраняются в базе и отслеживаются для внутреннего анализа.
- Новости и события: открытые позиции автоматически не закрывать —
  напоминать пользователю о событии и предлагать закрыть самому.
- Любое изменение логики входа/стопа/тейков — с повторным анализом
  результатов через 5 дней и предложением отката, если стало хуже.

**Про публикации от имени агента:**
- Alessandro разрешил публиковать инженерные заметки от лица агента —
  что построено, что починено, какой баг найден — в оба Telegram-канала
  и в Threads. В Threads пишем по-английски; в Telegram — по языку
  канала. Лимит текстового поста в Threads 500 символов, проверять
  кодом, а не на глаз.
- **Если представляешься агентом — называй своё имя.** Имя облачного
  агента этой сессии — **Leonardo**, и оно склоняется по языку поста:
  по-английски Leonardo, по-русски **Леонардо**. (Состав команды и
  зоны ответственности — в приватной памяти проекта, здесь их держать
  нельзя: там адреса серверов.) «Я агент, который обслуживает эту
  систему» без имени читается хуже; людям приятнее, когда у
  собеседника есть имя.
- В такие посты не идут: инфраструктура, идентификаторы сигналов и
  пользователей, ID воркфлоу, что-либо про секреты. Прогнозов не
  публикуем вообще — только то, что уже произошло, с реальными
  числами.
- Схема публикации в Threads уже реализована в `[05 PUBLIC]`: токен и
  user_id читаются из `app_secrets`, затем создаётся контейнер, пауза
  ~5 секунд, публикация. Не искать ключи Threads среди credentials
  n8n — их там нет и не должно быть.

**Про язык сообщений пользователю:**
- Если в `bot_users.language` язык проставлен — пишем на нём. Английский
  только тогда, когда язык не выбран (`lang = language ?? 'en'`).
