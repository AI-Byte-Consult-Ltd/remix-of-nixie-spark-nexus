# NICS AI Trader / AI Byte Consult — рабочая сводка для Claude

Этот файл — публичная часть проектной памяти: как собирать и деплоить
сайт, дисциплина работы с n8n, обязательные правила по секретам и
честности в продукте. Он специально краткий и не содержит ничего
приватного — репозиторий публичный.

**Приватная часть — команда, инфраструктура, разборы аварий, открытые
вопросы, продуктовый роадмап — живёт отдельно, не в git.** Загрузи её
в начале сессии: workflow `[00 OPS] Project Handbook` в n8n, ветка
`Show Handbook` (данные — таблица `project_handbook` в боевой базе).
Редактируется через форму `/form/nics-handbook` там же, доступ только
залогиненному в n8n; история версий не перезаписывается. Не полагайся
только на память чата: перед изменениями сверяйся с реальным
состоянием n8n (через MCP) и GitHub, они источник истины, а не файлы.

**В этот файл не писать**: IP серверов, hostname, пути на файловой
системе, имена баз данных, состояние или значения секретов, номера
ID workflow/credentials, что-либо, что раньше уже приводило к
случайной публикации приватной информации в этом самом публичном
репозитории. Всё это — в приватный рунбук.

Последнее обновление: 2026-08-26.

## Что это за проект

- **AI Byte Consult Ltd** (зарегистрирована в Болгарии) — этот
  репозиторий содержит публичный сайт (React/Vite/TS, деплой на
  GitHub Pages) и Telegram Mini App для продукта **NICS AI Trader**.
- Backend NICS AI Trader живёт **не в этом репозитории** — это n8n
  workflows на отдельном сервере, плюс MT5-мост на другом сервере.
  Детали — в приватном рунбуке.
- Отдельный репозиторий **`AI-Byte-Consult-Ltd/nics-ai-lab`** —
  обучение собственных моделей с нуля.

## Правила, которые нужно соблюдать

**Про базу:**
- **Никакого DDL в горячем пути.** `CREATE TABLE` / `ALTER TABLE` /
  `CREATE INDEX` — только разовая миграция, никогда не на каждый
  запрос. `IF NOT EXISTS` не делает операцию дешёвой: блокировка
  берётся всё равно (проверено на практике — см. приватный рунбук,
  раздел про аварию 6–7 августа).
- **Никаких разовых миграций данных на каждый запрос** — если видите
  в генерируемом SQL `DELETE`/`UPDATE` с пометкой «legacy» или
  «v1.x.x», это кандидат на вынос.
- Перед выводами о причинах тормозов — смотрите **тайминги по нодам**
  в конкретном execution, а не гадайте по коду.

**Про n8n:**
- После `update_workflow` **обязательно** `publish_workflow`. Правки
  через MCP попадают в черновик — пока не опубликовано, в проде
  ничего не меняется. Сверяйте `versionId` vs `activeVersionId`.
- Большие Code-ноды правьте с проверкой: после пуша перечитайте ноду
  и сравните дифом с локальной версией **до** публикации.
- Перед выводами о «что сейчас в проде» — сверяйтесь с реальными
  executions (`search_executions`/`get_execution`), а не с тем, что
  должно было получиться по коду.
- При добавлении нового инструмента/символа в один список (например,
  список поддерживаемых торговых инструментов) — проверяйте, нет ли
  где-то ещё параллельного списка того же назначения, который нужно
  обновить синхронно. Рассинхрон таких списков уже приводил к
  продакшн-авариям больше одного раза.

**Про секреты:**
- Никогда не печатать и не коммитить токены, пароли, API-ключи — ни
  в файлы, ни в комментарии, ни в чат.
- Не использовать `bash -x` в командах, где есть пароль или токен.
- Секреты для backend-сервисов (Telegram bot token и подобные) должны
  читаться из защищённого хранилища в момент выполнения, а не быть
  захардкожены в коде — так их можно ротировать в одном месте вместо
  правки множества файлов.
- `.env` в этом репозитории **не отслеживается git** — см.
  `.env.example` для списка нужных ключей. Помните: любая переменная
  с префиксом `VITE_` компилируется в публичный бандл и видна всем
  посетителям сайта — туда можно класть только то, что безопасно
  публиковать (например, Supabase anon-ключ, защищённый RLS), и
  никогда — серверные секреты.

**Про push в этот репозиторий:**
- Если у текущей сессии нет прав на запись в GitHub (403 при
  `git push` и через API) — это значит, что Claude GitHub App не
  установлен с правом записи для организации. Не пытайтесь обойти
  это самостоятельно: попросите владельца проекта установить
  приложение (github.com → Settings организации → Applications) и
  дать ему `Contents: Read and write`. Как временный запасной
  вариант — самодостаточный скрипт с изменениями (например, git
  bundle, закодированный в base64) для локального запуска владельцем;
  не отправляйте секреты в теле такого скрипта.

**Про деплой сайта:**
- `npm install && npm run build && npm run deploy` из актуального
  `main`; следить, что в `postbuild` вызывается
  `node scripts/generate-seo-pages.mjs`.

**Про честность в продукте:**
- На сайте и в отчётах — только реальные данные. Если процесс не
  идёт, честное состояние «offline», а не выдуманное число.
- Сертификаты, значки, подтверждения достижений — выдавать только за
  реально выполненное условие, не за факт оплаты или регистрации.
