встаёт в очередь до переподключения.

**Важно про безопасность этого канала.** Получатель не обязан доверять
входящему сообщению только потому, что оно пришло через триггер и
назвало правильное имя отправителя — 8 августа Stefano корректно
отказался выполнять и пересылать куда-либо результат аудита статистики
(агрегаты + рост объёма запроса до сырых данных с ценами исполнения),
потому что отправитель ссылался на устаревшую схему имён и не нашёлся
в его `ListAgents`. Это было ложное срабатывание (имена правда
разъехались), но сама проверка правильная и её нельзя «продавливать»
повторной отправкой через тот же автоматический канал — при расхождении
идентичности подтверждение должно приходить от живого человека, не от
ещё одного триггера. Итоговый результат аудита Stefano всё равно отдал
только в чат человеку, а не переслал дальше — это осталось верным
поведением по умолчанию для чувствительных данных.

Перед длинной задачей **всегда проверяйте, в какой вы сессии**: спросите

## Авария 6–7 августа и переезд базы (главное за сессию)

**Симптом**: бот отвечал по 34–51 секунде или падал с `ECHECKOUTTIMEOUT`,
запросы к базе шли по 50 секунд, пул подключений постоянно забит.

**Причины, найденные по порядку** (все реальные, все исправлены):

1. **DDL в горячем пути.** Нода `Ensure Bot Database Schema` в `[02 BOT]`
   на **каждое сообщение** выполняла блок `CREATE TABLE` / `ALTER TABLE
   ADD COLUMN IF NOT EXISTS` / `CREATE INDEX` по таблицам `signals` и
   `signal_deliveries`. `ADD COLUMN IF NOT EXISTS` берёт **ACCESS EXCLUSIVE**
   на таблицу ещё до того, как обнаружит, что колонка уже есть — то есть
   каждое сообщение боту дралось за самую тяжёлую блокировку Postgres
   с генератором сигналов и доставкой. Замерено: 21.5 сек ожидания на
   сообщение. Схема вынесена в разовую миграцию, нода переименована в
   `Apply Bot Maintenance` и содержит только регулярные `UPDATE`.
2. **То же самое в `Build Private Chat Confirmation Query`** — две строки
   `ALTER TABLE bot_users ADD COLUMN IF NOT EXISTS`. После правки первой
   ноды эта стала платить за блокировку сама (35.7 сек). Тоже убрано.
3. **`legacy_cleanup` в `[06 DATA]`** — разовая миграционная чистка
   (`DELETE ... WHERE source_utc_offset_seconds IS NULL`) выполнялась на
   каждый входящий запрос, ~25 раз в минуту, круглосуточно. Убрано:
   приём котировок ускорился со 146–448 мс до 25–39 мс.
4. **Корень всего — тариф.** База жила на **Supabase free tier**
   (`eklohkggksnphhqhvmoa`, инстанс t3a.nano). Disk IO budget был выбран
   на 100%, compute 100%, статус Unhealthy, 58% успешных запросов за час,
   лимит пула 15 сессионных подключений, **бэкапов не было вообще**.

**Решение**: база перенесена на Oracle (`pg_dump -Fc` → локальный
`postgres:16`). Данные сверены: 191 сигнал, из них 74 закрытых,
8 пользователей, 185 доставок. `broker_market_candles` перенесена без
данных — свечи мост заливает заново.

**Результат**: бот 34–51 сек → **0.4–0.6 сек**, запрос статистики
632 мс → **32 мс**, приём котировок → **25–39 мс**.

Проект Supabase пока **не удалён**, держится как страховка.

## Правила, которые нужно соблюдать

**Про базу:**
- **Никакого DDL в горячем пути.** `CREATE TABLE` / `ALTER TABLE` /
  `CREATE INDEX` — только разовая миграция, никогда не на каждый запрос.
  `IF NOT EXISTS` не делает операцию дешёвой: блокировка берётся всё равно.
- **Никаких разовых миграций данных на каждый запрос** — если видите в
  генерируемом SQL `DELETE`/`UPDATE` с пометкой «legacy» или «v1.x.x»,
  это кандидат на вынос.
- Перед выводами о причинах тормозов — смотрите **тайминги по нодам**
  в конкретном execution, а не гадайте по коду.

**Про n8n:**
- После `update_workflow` **обязательно** `publish_workflow`.
- Большие Code-ноды правьте с проверкой: после пуша перечитайте ноду
  и сравните дифом с локальной версией **до** публикации.
- Перед выводами о «что сейчас в проде» — сверяйтесь с реальными
  executions (`search_executions`/`get_execution`).

**Про секреты:**
- Никогда не печатать и не коммитить Telegram-токен, `_internalKey`,
  пароли базы, ключи R2/Supabase — ни в файлы, ни в комментарии, ни в чат.
- Не использовать `bash -x` в командах, где есть пароль.
- Дампы базы содержат таблицу `app_secrets` → `chmod 600`, наружу не отдавать.

**Про деплой сайта:**
- `npm install && npm run build && npm run deploy` из актуального `main`;
  следить, что в `postbuild` вызывается `node scripts/generate-seo-pages.mjs`.

**Про честность в продукте:**
- На сайте и в отчётах — только реальные данные. Если процесс не идёт,
  честное состояние «offline», а не выдуманное число. Сфабрикованные
  отзывы и фейковые «живые» метрики обучения уже удалялись однажды;
  не возвращать.
